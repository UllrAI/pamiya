# Pamiya 首版范围与架构取舍

Pamiya 保留控制、状态与执行分离，采用轻量首版机制。跨节点接管、离线授权、严格费用预算与自动灾备在具体需求出现时启用，不提前成为每个任务的通用门槛。

导航：[文档索引](README.md) · [协议](capabilities-and-protocol.md) · [恢复与验收](reliability.md)

## 保留的首版要求

| 要求 | 为什么保留 | 最小实现 |
|---|---|---|
| Task/Attempt 持久化 | 崩溃后知道任务发给谁、执行到哪 | Task 表、轮次与条件更新 |
| 可靠发布与结果确认 | MQTT 不判定业务完成，消息可能重复 | 扫描、ACCEPTED、终态与 RESULT_ACK |
| 工具调用与执行去重 | 同一模型回复或命令不能创建重复动作 | 稳定 tool_call_id、event_id 与一份本地执行记录 |
| Session 与设备串行 | 对同一上下文和现场的冲突是实际需求 | 一个活跃控制者、固定设备归属、占用与本地队列 |
| 最小身份与权限隔离 | 多租户与用户设备不能互相调用 | TLS、凭据、Topic ACL、能力和资源范围检查 |
| 开始期限与取消记录 | 重连后的旧命令不能无条件执行 | start_deadline、max_runtime_ms、Task canceled 标记 |
| 大文件引用与关联 | MQTT 不承担所有文件传输，结果要对应实际内容 | 独立 key、摘要、上传校验与数据库引用 |
| 未知重要效果核对 | 重发消息不能解决动作已经发生的歧义 | 查询或观测，不盲目重放 |

这些机制与首版现有对象合并实现。Inbox 是去重责任，不必独立服务；取消墓碑是 Task 中的小记录，不必另建墓碑系统；审批是有条件的业务状态，不必先建设策略引擎。

## 过度设计及收敛结果

| 原要求 | 问题 | 首版采用 | 重新引入的触发条件 |
|---|---|---|---|
| 每 Task 都携带租约、资源 fence 与续租版本 | 固定归属和不自动接管时成本高于收益 | attempt_no、设备占用、短任务时限 | 多控制者或 Worker 自动接管同一资源 |
| 签名 ExecutionGrant 与每动作在线核验 | 在已认证的 Control/Broker/Worker 信任边界内重复授权 | Control 检查、ACL、固定能力范围 | 离线授权、跨组织信任或严格即时撤销 |
| registration_epoch、挑战与 Broker 连接事件同时存在 | 多种连接确认机制叠加 | connection_id、注册响应、业务心跳 | 规模或接入环境证明需要更强注册归属 |
| 独立 RuntimeStep、Approval、TriggerRecord、BudgetReservation 体系 | 概念职责被过早变成子系统 | 检查点在 Run，工具关联和审批在 Task，触发状态在 Event | 历史查询、复杂规则、并行预算确有需要 |
| 所有文件强制 staging、复制、finalize | 普通可信 Worker 产物增加网络和存储操作 | 原生写一次条件或版本，摘要与结果关联 | 不可信上传、内容扫描、证据封存 |
| control_epoch 是首版上线前置 | 将手动恢复扩展成自动灾备平台 | 暂停派发、确认旧进程停止、人工对账 | 自动恢复、旧控制者存活或离线授权 |
| 通用预算预留与结算账本 | 普通迭代限额被升级为账务系统 | 迭代、时长、数量、并发上限和用量记录 | 严格共享费用预算或按量结算 |
| 全套窗口、规则版本、历史重放 | 简单主动触发不需要完整事件平台 | 新鲜度、过滤、冷却和事件去重 | 明确的窗口聚合、重放或审计需求 |
| 条件功能的所有故障都必须首版注入 | 首版验收与未实现功能混在一起 | 只验已采用能力及基本备份恢复流程 | 启用增强能力时追加对应测试 |

单活并非忽略并发：Task 条件更新、工具调用唯一性和 Worker 串行仍保留。增加多活接管前补齐资源 fencing，而不是在它尚无作用的阶段预先实现整套协议。

## 过度防护及适用范围

| 原表述倾向 | 调整后 |
|---|---|
| 有副作用就审批或在线核验 | 既有授权覆盖的操作直接执行；只有范围不足或明确策略要求才请求确认 |
| 任意未知结果都要人工核对 | 只读可重试、导航可重观测；无法核对的重要一次性效果才人工处理 |
| 所有 HID 点击都要排除人工并发 | 普通导航和滚动自动处理画面变化，发送等关键动作再核对 |
| 一个设备不明就冻结后续工作 | 只暂停可能冲突的资源，独立 Run、其他设备与只读能力继续 |
| 收到消息也不能信任任何组件 | 明确首版信任已认证的控制服务与自有 Worker，仍做 Schema、范围、期限和状态检查 |
| 取消要求瞬间撤销所有在途动作 | 首版尽力停止并报告真实状态；严格即时撤销是单独的业务要求 |

不把签名、容器或审批叠加视为天然更安全：它们需要对应的威胁、权限或隔离边界。云端执行不可信代码时需要沙箱；固定指令的 ESP32 不因此必须拥有相同隔离实现。用户桌面按授权范围执行，也不意味着所有文件操作都必须云端审批。

持久化粒度同样按工具意图选择：平台保存一次工具调用或目标委托，Worker 内部的鼠标校准、按键扫描码、图像分片和本地轮询不各自成为 Task。模型流式 token 不进入任务调度表，只有恢复需要的回复、工具关联、结果和检查点进入持久化状态。

## 首版的明确取舍

当前设计不承诺多活自动接管、不可逆动作恰好一次、即时撤销离线授权、任意厂商进行中会话无损迁移，或严格全局费用上限。相应目标有真实需求时，通过 05 的阶段与本表条件补齐。

同时不能删除 Task/Attempt 的区别、设备与 Environment 的语义、重要结果的业务确认、用户与租户的权限归属，以及未知重要效果的记录。简化应删除冗余机制，不让开发者以后重新发现这些关键边界。

## 验证与维护

正文的协议示例采用首版字段，条件增强字段独立说明；故障矩阵分为首版场景和按启用功能追加的验收。JSON、链接、模型关联与图表仍需保持一致。实际 Worker、Broker、SDK 与设备行为由实施阶段验证，不以文档中的条件增强描述宣称已经具备。

后续评审一项机制时，先说明具体触发场景、它阻止的故障、已有实现为何不足，以及最小可用替代。没有当前需求或明确触发条件的机制不进入首版验收。
